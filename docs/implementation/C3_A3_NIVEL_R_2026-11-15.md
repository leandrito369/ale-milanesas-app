## 1. Objetivo

Observar y verificar dos intercalados reales R usando el código de servicio integrado, PostgreSQL 17.11 y Testcontainers, con barreras por bloqueo de fila y prueba de espera mediante `pg_locks`, `pg_stat_activity` y `pg_blocking_pids`. Ninguna transacción de laboratorio usa la base Compose dev/l05. **El éxito de dos escenarios no demuestra ausencia global de deadlocks.**

## 3. Harness de Nivel R

Archivo: `src/test/java/ar/edu/unam/alemilanesas/concurrencia/C3A3ServiciosRealesIntegrationTest.java`.

- Testcontainers arranca PostgreSQL 17.11 efímero. Flyway aplica migraciones V1–V3 de la aplicación; no V4.
- Hay dos tareas de servicios reales y una tercera conexión controladora.
- La controladora bloquea una fila PostgreSQL para fijar el punto de espera. En ningún caso se simula que UC-05/07/41 existan.
- Antes de liberar la barrera se observa el holder de `A1(bigint)`, su espera de fila y una segunda transacción en espera del mismo advisory lock.
- El harness utiliza espera de condición (Awaitility) sobre locks observables, **no sleeps para ordenar intercalados**.
- Tras liberar la conexión controladora, ambos servicios deben terminar y se cotejan hechos persistidos.

### C3-01

1. Crear Pedido, Receta, Insumos y Partidas a partir de `PreparacionFixture`.
2. Crear un CLIENTE sintético con `idCliente = idInsumo`.
3. Conexión controladora retiene `PRECIO_PRODUCTO FOR UPDATE`; UC-03 toma `A1(idCliente)` y espera precio.
4. UC-28 toma `PEDIDO U → DETALLE U → A2(808,0)` y espera `A1(idInsumo)`.
5. Observar bloqueo real; liberar barrera; afirmar alta de Pedido y preparación única con stock y partida coherentes.

**Afirmación limitada:** colisión entre namespaces A1 de dos dominios distintos causa falsa contención; no provoca 40P01 en este intercalado.

### C3-02

1. Crear CLIENTE sintético `2929001` y un Pedido inicial de ese Cliente.
2. Conexión controladora retiene `CLIENTE FOR UPDATE`.
3. UC-29 obtiene `A1(2929001)` y espera `CLIENTE U`; UC-03 solicita el mismo advisory A1.
4. Observar y liberar; afirmar un COBRO, un MOVIMIENTO_CAJA y alta de segundo Pedido, sin efectos duplicados.

**Afirmación limitada:** serialización en advisory compartido A1, no cobertura general de UC-29 ni de rendiciones UC-05.

## 4. Ejecución

```bash
mvn -B -ntp -Dtest=C3A3ServiciosRealesIntegrationTest test
```

La PR dispara el workflow existente `B1 - Maven / Testcontainers PostgreSQL`, que ejecuta `mvn -B -ntp clean verify`. El cierre exige reporte Surefire del SHA exacto, cero fallos y que los nuevos tests realmente aparezcan en los resultados. Los tests no se consideran PASADOS antes de ver los logs del workflow.

## 5. Registro obligatorio de evidencia

| Campo | Requisito |
|---|---|
| Commit SHA | Exacto del workflow y de test |
| PostgreSQL | 17.11 y arranque de contenedor |
| Flyway | V1–V3 aplicadas |

El harness observa esperas mediante `pg_locks`, pero en esta versión solo las **aserta**; no publica las trazas completas a un artefacto serializado. No afirmar que hay capturas de `pg_locks` conservadas si no están en un artefacto verificable.

## 6. Riesgos excluidos de esta PR

- No demuestra que UC-43 y UC-05 tengan un ciclo de deadlock: `FOR SHARE` de USUARIO con otro `FOR SHARE` es compatible; para afirmar ciclo se debe probar la segunda arista incompatible.
- No mide rendimiento/P99 ni corrige colisiones en producción.
- No modifica `ActualizarPrecioVigenteService` ni su `clock_timestamp()`; ese hallazgo requiere investigación independiente.
- No diseña un orden ratificado para UC-05/06/07/41 ni generadores de EXCEDENTE.
- No ejecuta CR-C/CR-F, V4, O1/O2, funciones SQL candidatas, ni toca bases persistentes.
- No autoriza despliegue, RD, controles D/E/F/G ni cierre de H.
