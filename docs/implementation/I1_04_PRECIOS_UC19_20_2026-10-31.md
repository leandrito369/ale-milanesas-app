## UC-19: actualización transaccional

- Solo ADMINISTRADOR con sesión vigente y rol revalidado tras bloqueo. Un UUID de `SESION_USUARIO` es contexto interno, no token HTTP.
- Producto debe existir y estar activo. Se toma `SELECT "PRODUCTO" FOR UPDATE` antes de generar/insertar `PRECIO_PRODUCTO`; este bloqueo es más fuerte que el `FOR SHARE` acordado para insertar una relación y serializa con UC47/48. Los múltiples precios del mismo Producto quedan serializados por fila padre.
- `vigenteDesde` no puede ser anterior al instante actual **de PostgreSQL**; `vigenteHasta` es opcional, **exclusivo** y mayor que el inicio. `precioBase>0`, NUMERIC(18,4). Entradas se transportan como `OffsetDateTime` para preservar el instante de TIMESTAMPTZ.
- La regla física `ex_precio_producto_no_solape` sobre rangos `[desde,hasta)` impide vigencias superpuestas. El servicio valida intervalos antes de alterar filas y rechaza nuevas programaciones que solapen un precio futuro. Si existe un período previo que cubre el nuevo inicio, lo **cierra** en `vigenteDesde` y conserva su `idPrecio`, `precioBase` y `fechaHoraRegistro`. Nueva fila y auditorías dentro de una sola `@Transactional`. No se sobrescriben precios históricos ni valores congelados en `DETALLE_PEDIDO`.
- Se registran eventos: `CIERRE_VIGENCIA` del precio previo (antes/después del fin), y `MODIFICACION_PROGRAMADA` del precio creado con valores anterior/nuevo. No se inventa `ALTA_PRECIO`. **Interpretación aprobada por [RD-UC19-001](https://github.com/leandrito369/ale-milanesas/blob/main/docs/01-gobierno/b0/RD_UC19_001_AUDITORIA_PRIMER_PRECIO_2026-11-01.md):** MR5 sólo admite `MODIFICACION_PROGRAMADA`, `CANCELACION_PROGRAMADA`, `CIERRE_VIGENCIA`. Para el **primer precio** se registra `MODIFICACION_PROGRAMADA` con `precioAnterior=NULL`, anterior de vigencia NULL, precio nuevo y fecha nuevos, actor y fecha reales. No se simula una modificación de precio previamente existente ni se incorpora `ALTA_PRECIO`.
- `idPrecio` y `idAuditoriaPrecio` BIGINT no tienen secuencias MR5; se usa lock transaccional `pg_advisory_xact_lock(1919001)` seguido de `MAX+1`. No asegura interoperabilidad con escritores externos que no utilicen el protocolo. No se agregan migraciones.
- La API interna **no cancela precios programados** ni altera registros cancelados: fuera de alcance UC19; los eventos `CANCELACION_PROGRAMADA` sólo se leen en UC20.

## UC-20: historia y auditoría

- Solo ADMINISTRADOR. Consulta de solo lectura de las filas `PRECIO_PRODUCTO` y eventos reales `AUDITORIA_PRECIO`, sin fabricar versiones ni movimientos.
- Distinción `HISTORICO`, `ACTUAL`, `FUTURO`, `CANCELADO` según una marca temporal PostgreSQL por consulta. La versión `ACTUAL` está identificada por id (o ausente); no asumir que un precio programado ya está vigente.
- Filtros `LocalDate` de rango inclusivo en zona comercial explícita `America/Argentina/Buenos_Aires`, traducidos al intervalo `[inicioDelDía, inicioDíaSiguiente)` para buscar períodos de vigencia que se intersectan. Las auditorías se limitan a los precios seleccionados y se ordenan por `fechaHoraEvento`.
- No confundir `fechaHoraRegistro` con inicio de vigencia ni con `fechaHoraEvento`. Si un filtro temporal excluye el precio actual, `idPrecioActual` en la respuesta filtrada es NULL; para saber el actual global, consultar sin filtro.

## Riesgos y puertas

1. **RD-UC19-001 APROBADA (01/11/2026):** primer precio mapeado a `MODIFICACION_PROGRAMADA` con `precioAnterior=NULL`. Esta reserva específica está resuelta en [Issue #21](https://github.com/leandrito369/ale-milanesas-app/issues/21) cerrada; no acredita B4 ni revisión de código.
2. El algoritmo de cierre se limita a un período válido previo cuya vigencia cruza la nueva fecha. No reescribe otras programaciones; si se quiere editar/cancelar programación futura se necesita contrato específico (y el motivo/auditoría correspondiente).
3. F09 y las FK no suplen el bloqueo explícito y la revalidación comercial de Producto. Adoptar orden por id al bloquear listas de Productos para UC03/10/21/24 y orden topológico CLIENTE → PRODUCTO → INSUMO → hijas en flujos multi-entidad. No atribuir estas garantías a futuros servicios aún inexistentes.
4. UC-35 proviene de PR #18. La PR integrada #26 reúne esa dependencia, UC-19/20, Cliente, Insumo y Cobro; los resultados de B1/B2 deben siempre referirse al SHA conjunto, no a PR #20 aislada.
5. MR5/F01 no cambian, no se implementa F04/S01. B4 se habilitará únicamente al finalizar Iteración 1; BC06 0/18 E2E y cuatro UC54 documentados no se acreditan aquí.
